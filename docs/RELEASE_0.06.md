# 0.06: 검증을 통과한 ONNX Runtime 설정으로 내보내기

사용자 Windows 화면의 0.05 진단에서 `ONNX Runtime 최적화를 끄면 통과함`이 확인됐다.
하지만 진단 결과가 실제 내보내기에 연결되지 않아 실패로 끝났고, Python·C++ 배포
추론기도 최적화를 항상 ALL로 켰다. 이 두 연결 누락을 수정한다. 특정 ORT 최적화
패스의 결함이나 학습 불량으로 단정하지 않으며, 기존 체크포인트로 다시 내보낼 수 있다.

## 변경

- EfficientNet의 사전 융합·원본 그래프가 기본 설정에서 실패하면, 원본 그래프를
  스레드 수를 제한한 ALL/BASIC/DISABLED 설정으로 순서대로 재검증한다.
- 각 설정에서 seeded·zero 입력과 선택한 동적 배치(batch 2)를 모두 검사한다.
  0.05 진단 한 건이 통과했다는 이유만으로 저장하지 않는다. logits 허용 오차
  `atol=1e-3, rtol=5e-4`, 유한성·형상·top-1 조건을 유지한다.
- 통과한 실행 설정과 검증 이력을 JSON에 저장한다. 이 경우 schema 6으로 기록해
  구형 SDK가 설정을 무시하고 ALL로 실행하는 것을 막는다. 기존 schema 5도 지원한다.
- Python `OnnxClassifier`, C++17 `VisionInference`, C ABI와 C#의 `Open`/`OpenBundle`이
  저장한 설정을 적용한다. C++ 백그라운드 작업과 C# 샘플은 기본적으로 JSON의
  스레드 수를 사용한다. 스레드 수를 명시적으로 바꾸면 그 환경에서 다시 검증해야 한다.
- 앱 CPU 추론의 원본 그래프 재시도도 상수 폴딩을 제외해 내보내기와 조건을 맞춘다.
- 모든 설정이 실패할 때는 기존 배포 파일을 보존하고 수치 진단을 남긴다.

설정 예시(스레드 수는 실제 검증 값으로 저장):

```json
{
  "schema_version": 6,
  "num_threads": 4,
  "onnxruntime": {"graph_optimization_level": "disabled"}
}
```

ONNX와 JSON을 함께 배포하고 0.06 이상의 SDK를 사용한다. 추론 속도는 설정 변경으로
달라질 수 있다. Windows/i7의 8 ms 달성이나 비공개 모델의 최종 배포 성공을 확인한
것은 아니며, 실제 PC의 내보내기 성공과 추론 시간을 별도로 확인해야 한다.

## 검증 방법

실제 B0 1×1×224×224 ONNX에 최적화 출력 오류를 주입해 BASIC/DISABLED 재시도,
전체 입력 검증, JSON 저장, 배포 번들 생성 및 Python 추론 재사용을 검사한다.
seeded 입력만 통과하고 zero 입력이 실패하는 경우에는 저장을 거부하는지도 검사한다.

별도로 실제 FP32 상쇄 오차가 발생하는 작은 Conv/BatchNorm ONNX를 사용한다.
`1 * 1e8 - 1e8` 계산 후 BatchNorm의 1을 더하면 1이지만, 최적화로 1을 Conv bias에
미리 합치면 FP32 반올림으로 0이 된다. Python·C++17·C ABI·백그라운드 작업에서
최적화를 끈 설정이 계산 결과에 실제 반영되는지 검사한다. 이 인공 모델은 사용자의
가중치나 정확한 오차 28.597656을 재현한 모델은 아니다.

로컬 macOS ARM64에서 Python 관련 검사 63개가 통과했다. ONNX Runtime 1.29.0으로
C++17 Release 빌드와 CTest 4개를 통과했고, .NET 8 C# 샘플도 같은 schema 6 번들을
실제로 열어 기대 확률 0.880797을 반환했다. Windows 결과는 해당 커밋의 자동 검사에서
별도로 확인한다.
