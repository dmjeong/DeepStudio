# C++ 출력 검사 지연 수정 (2026-11-10)

## 계획 / 원인

- 사용자 측정: 모델 실행 600ms, `ValidateOutput` 1초 이상.
- `cpp/src/vision_inference.cpp`의 반복 조건이 `info.GetElementCount()`를 호출한다. ORT C++ 헤더에서 이 함수는 C API `GetTensorShapeElementCount` 호출 및 상태 검사를 수행한다.
- 출력 `[1, 5, 1504, 3520]`은 26,470,400개 float이다. 반복 조건 때문에 동일한 개수 조회를 26,470,401번 수행한다.
- Re-DETR 점수·박스 검사에도 같은 반복 조건이 있다.

## 설계

- 텐서마다 개수를 한 번 받아 `const size_t`에 저장하고 순회한다.
- 전체 원소의 NaN/Inf 검사, 자료형·차원·클래스 수 검사와 오류 문구를 유지한다. 샘플링·검사 생략·fast-math를 도입하지 않는다.
- 모델·전처리·후처리 계산과 스레드 설정은 바꾸지 않는다. 재학습·ONNX 재생성이 필요 없는 SDK 수정이다.

## 검증 계획

- 동일 ORT 텐서에서 수정 전후 검사 함수 자체의 중앙값을 측정한다. Release와 비최적화 빌드를 구분하고 대상 PC 성능으로 일반화하지 않는다.
- 실제 배포 엔진의 Segment/Detect 호출에 NaN, +Inf, -Inf를 주입한다. 분할 출력의 시작·중간·끝에 주입해 검사가 끝까지 유지되는지 확인한다.
- 기존 C++ 배포·암호화·C ABI·동시성 검사 및 세그멘테이션 Python/C++ 일치 검사를 실행한다.
- 합성 출력의 검사 비용 측정은 실제 모델 추론 속도나 정확도 평가가 아니다.

## 추가 요청: 전처리 200ms / 스레드를 늘려도 효과 없음

- 사용자 답변: Debug 빌드에서 측정했다. 최종 성능은 Release/x64에서 별도로 측정해야 한다.
- 크롭은 `cv::Mat` ROI 참조로 수행한다. 픽셀 복사 비용은 이후 색 변환·정규화에서 발생한다.
- 전체 영역 전처리는 각 픽셀·채널에 두 번의 나눗셈을 하는 단일 스레드 반복문이다. `num_threads`는 ORT `SetIntraOpNumThreads`에 전달되며 이 반복문을 병렬화하지 않는다.
- 0..255 값 각각에 기존 float 정규화 식을 그대로 계산한 표를 만들고 재사용한다. 채널별 연속 쓰기로 변경한다. 병렬 풀이나 전역 OpenCV 스레드 설정은 추가하지 않는다.
- 전체 입력 텐서의 bitwise 일치, RGB/gray, 비연속 ROI, 패딩, 정상화 계수를 검증한다. 색 변환 및 resize 순서는 유지한다.
