# 분할 추론 스레드 확장·직렬 구간 검토

## 결론

스레드 설정 누락은 확인되지 않았다. `InitializeFromJson`의 마지막 인자는 JSON보다 우선하고 세션 생성 시 `SetIntraOpNumThreads`로 전달된다. 로컬 ORT 프로파일에서도 4스레드 설정으로 주 스레드와 작업 스레드 3개가 실제 합성곱에 참여했다.

하지만 사용자의 Windows PC에서 4개 이후 성능이 포화되는 원인을 메모리 대역폭 하나로 확정할 수는 없다. 사용자 측정은 전체 약 1.2초이고, 구간별 로그는 아직 받지 않았다. 다음 결과는 코드 검토와 독립적인 로컬 실험이다.

안전하게 줄일 수 있는 직렬 작업을 확인했다. 배경 픽셀 확률 계산 생략 및 결함 영역 내 점수 집계는 실험에서 결과를 유지했다. U-Net ResNet18은 모델 내부의 큰 디코더 합성곱·특징 복사·확대도 무겁다. 후처리 최적화만으로 이 모델을 몇 배 가속한다고 주장할 근거는 없다.

## 측정 조건과 한계

- macOS Apple M4: 성능 코어 4개 + 효율 코어 6개. 사용자의 Windows/i7 또는 Xeon과 코어·커널·메모리 특성이 다르다. 로컬에서 4 이후 포화된 결과를 사용자 PC 원인의 증명으로 삼지 않는다.
- C++17 Release `-O3 -DNDEBUG`, ORT 1.29.0 CPU/ALL, OpenCV 4.12.0/1스레드.
- 이전에 합성 트레이로 실제 학습했던 U-Net Lite와 U-Net ResNet18, **FP32·3클래스** ONNX. 사용자의 INT8·5클래스 모델 측정이 아니다.
- 입력 영상 3504×1504, ONNX 입력 3520×1504. `test_00` 합성 영상 한 장. 두 모델 모두 예측 픽셀의 약 99.98%가 배경이라 배경 확률 생략 효과가 크다. 전경이 많으면 이득은 감소한다.
- 실행 파일에서 세션을 새로 만들고 동일 크기로 2회 워밍업. 스레드 비교 5회, 후처리 후보 비교 7회 중앙값. 4스레드 기준을 마지막에 재측정했다. 생산 p95 보장용 표본 수가 아니다.
- 여러 모델을 동시에 측정하지 않았다. 시계 측정과 마스크 해시/파일 저장도 분리했다. 표의 각 열은 해당 구간의 중앙값이라 서로 합산한 값이 전체 중앙값과 정확히 같을 필요는 없다.

## 2. 출력·판정을 보존하는 후처리 후보

실험용 C++ 소스에서만 변경했다. 제품 소스에는 아직 적용하지 않았다.

### 배경 픽셀의 softmax 생략

`Segment`는 현재 모든 픽셀의 최대 클래스를 구한 뒤, 결함 기준이 있으면 배경까지 softmax를 계산한다. 반면 `ApplyDefectRules`는 클래스 1 이상만 평가하며 배경의 확률을 읽지 않는다.

- argmax가 0인 픽셀의 임시 확률을 0으로 놓고 softmax를 생략한다.
- 전경 픽셀의 확률 계산 순서·정밀도는 유지한다. NaN/Inf 검사는 전체 출력에 그대로 적용한다.
- Lite의 decode: 38.28 → 4.84ms. 전체 281.63 → 248.37ms (재측정 기준 279.37ms).
- ResNet18의 decode: 38.92 → 4.84ms. 모델 계산이 지배적이므로 전체 개선 비율은 작다.

### 덩어리 상자 안에서 점수 집계 / 제거가 없으면 지우기 생략

현재는 클래스별 연결 요소 계산 후 점수·면적 집계에서 전체 영상을 훑고, 제거할 결함이 없어도 다시 전체 영상을 훑는다.

- 연결 요소의 bounding box 안에서만 해당 label의 픽셀을 집계한다.
- 덩어리별 픽셀의 행 우선 누적 순서는 그대로라 double 합산 순서가 유지된다.
- 상자 면적의 합이 전체 영상 이상이면 기존 전체 순회를 사용한다. 복잡한 중첩 상자에서 손해가 커지는 것을 막는다.
- 제거할 덩어리가 없으면 지우기 순회 자체를 생략한다.
- Lite rules: 19.03 → 13.49ms. 두 변경을 합친 전체: 242.80ms.
- ResNet18 rules: 20.03 → 13.66ms. 모델 시간을 빼고 보면 줄어든 후처리 비용은 약 40ms 수준이다.

### 일치 검사

- 두 학습 모델의 원본·후보 결과: 클래스 ID 마스크, 유효 영역, 컬러 마스크, 클래스별 픽셀 수, 제거 개수, 결함 클래스·상자·면적·점수 모두 동일.
- 추가 5클래스 고정 출력 12종: 전부 배경/밀집 전경/희소 결함/겹치는 상자 형태 × 원배율/축소/확대. 점수 동점과 작은 결함, 클래스별 제거 기준 포함. 원본과 두 후보의 결과 모두 동일.
- 이 검사는 후처리 변경의 동등성 검사다. 모델의 생산 검출률이 좋다는 의미는 아니다.

## 3. U-Net ResNet18 내부 비용

`python/builtin_models.py`의 `UNetResNet18.forward`는 마지막에 다음 순서로 계산한다.

```text
64채널, 절반 해상도 특징
  → 64채널을 원본 해상도로 bilinear 확대
  → 1×1 Conv로 클래스 수로 축소
```

3520×1504 FP32 64채널 중간 텐서는 약 **1.355GB**다. 사용자처럼 5클래스인 최종 출력은 약 106MB다. 이는 텐서의 논리 크기이며, 프로세스 최고 메모리 사용량을 측정한 값은 아니다.

4스레드 ORT 프로파일에서 큰 비용의 예:

| 연산 | 약 ms | 출력 |
|---|---:|---|
| 마지막 디코더 첫 3×3 합성곱 | 193 | `[1,752,1760,64]` |
| 마지막 디코더 두 번째 3×3 합성곱 | 128 | `[1,752,1760,64]` |
| 마지막 64채널 확대 | 100 | `[1,64,1504,3520]` |
| 마지막 skip 결합 | 99 | 큰 특징 텐서 결합 |

프로파일은 오버헤드가 있으므로 표를 그대로 일반 실행 시간에 더하지 않는다. 계산과 메모리 이동이 모두 큰 구조임을 확인한 것이며, 메모리 대역폭 포화를 하드웨어 카운터로 입증한 것은 아니다.

### 마지막 1×1 Conv를 먼저 적용하는 후보

실험 ONNX에서 마지막 두 연산만 바꿨다. 입력 해상도·특징 추출기·디코더 채널 수는 유지한다.

```text
64채널, 절반 해상도 특징
  → 1×1 Conv로 클래스별 점수 계산
  → 점수 지도를 원본 해상도로 bilinear 확대
```

선형 보간과 위치마다 같은 1×1 affine 변환은 실수 수학에서 교환할 수 있지만, FP32 연산 순서가 달라져 비트 단위로 같지는 않다. INT8의 Q/DQ까지 포함한 교환을 보장하지 않는다.

- ResNet18 모델 계산: 원본 재측정 범위 1340~1362ms → 후보 1255ms, 약 **6~8% 감소**.
- 8스레드 후보 모델 1287ms로, 이 후보도 스레드 증가만으로 계속 빨라지지 않았다.
- 같은 합성 영상에서 logit 최대 절대 차이 `6.67572021484375e-06`.
- 5,294,080 출력 픽셀의 argmax 변경 0개. C++ 판정 결과도 동일.
- 한 영상의 FP32 비교다. 사용자의 INT8 모델로 적용하려면 FP32 후보 검증 후 다시 calibration/quantization하고 판정 검증해야 한다. 그대로 파일을 바꿔 배포할 수준의 검증은 아니다.

## 적용 우선순위

1. 앞서 만든 11.82 구간 계측으로 사용자 Release/x64의 4·8스레드 `model/decode/rules/render`를 확인한다.
2. 배경 확률 생략과 불필요한 전체 영상 순회를 우선 적용한다. 모델·해상도·정밀도를 바꾸지 않는 SDK 최적화이며 재학습·ONNX 재내보내기는 필요 없다.
3. ResNet18인 경우 마지막 1×1 Conv/확대 순서 변경을 선택적 export 후보로 검증한다. 새로운 내보내기 및 INT8 재보정이 필요하다.
4. 더 큰 개선이 필요하면 마지막 디코더의 무거운 3×3 합성곱 자체를 줄이는 구조를 별도 모델로 연구한다. 해상도를 유지할 수 있어도 표현력이 달라지므로 재학습·정확도 평가가 필요하다. 이번 검토에서 임의로 교체하지 않았다.
