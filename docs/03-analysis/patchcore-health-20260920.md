# PatchCore 동작 및 검출 품질 검토

검토일: 2026-09-20. 대상: `5df833b`의 Python/GUI 구현.
요청: 학습이 매우 빨리 끝나고 정상·불량을 구분하지 못하는 것처럼 보이는 원인 분석.

## 결론

짧은 학습 시간 자체는 정상이다. PatchCore는 사전학습 CNN의 가중치를 고정하고 정상 이미지에서 특징을 추출하여 대표 특징을 저장한다. 일반 분류 모델처럼 여러 에폭 동안 역전파하지 않는다.

현재 구현의 특징 추출, 메모리 뱅크 구축, 저장·복원, 추론 경로는 작동한다. 하지만 **동작 검증과 실제 불량 검출 성능 검증은 다르다.** 임계값 보정, 평가 데이터 선택, 점수 계산 및 표시 방식에 아래 문제가 있으므로 현재 제품 상태를 검출 품질까지 정상이라고 판정할 수 없다. 사용자의 비공개 데이터·체크포인트·실행 로그는 확인하지 않았으므로 특정 원인이 사용자의 증상을 일으켰다고 단정하지 않는다.

## 확인한 정상 동작

- `python/patchcore.py:307`: 학습 로더의 모든 배치를 한 번씩 처리한다. 학습 로더는 `drop_last=False`다.
- 기본 ImageNet 백본 다운로드/로드 실패를 무작위 가중치로 대체하지 않는다. 백본과 BatchNorm은 고정된다.
- 현재 체크포인트는 백본 가중치와 메모리 뱅크를 함께 저장한다. 저장·복원 후 추론 일치 테스트가 있다.
- 기본 224 입력은 이미지당 28×28=784개 패치 특징을 만든다. 100장이면 78,400개 특징을 관찰하고 기본 한도에서 후보 20,000개, 대표 약 784개를 선택한다. 대표 비율 1% 자체만으로 오류라고 볼 수는 없다.
- 학습한 이미지 수가 많지 않으면 수 초 이하의 특징 구축도 가능하다. 에폭 수를 늘리는 것은 이 방식의 해결책이 아니다.

## 문제와 영향

### 1. 메모리 구축 완료와 판정 준비 완료가 구분되지 않음

`gui/core/patchcore_trainer.py:180` 이후 평가 데이터가 없거나 정상/불량 두 클래스가 없으면 임계값이 `None`인 상태로 저장된다. 그래도 실행 기록은 `completed`, 마지막 로그는 `PatchCore 완료`다.

이는 특징 학습 실패는 아니지만, 사용자가 판정까지 준비됐다고 오해하기 쉽다. 현재 자동 임계값은 정상·불량 라벨을 모두 요구한다. 이는 현재 프로그램의 보정 정책이며 PatchCore 학습 자체에 불량 이미지가 필요하다는 의미는 아니다. 추론은 임계값 부재를 `uncalibrated`로 표시하며 자동으로 정상 판정하지 않는다.

### 2. 평가 폴더 선택과 GUI의 불일치 — 재현됨

`python/patchcore_data.py:43`: 첫 번째 비어 있지 않은 `val`, `test` 순서로 평가 폴더를 선택한다. 클래스 구성이 적합한지는 선택 전에 확인하지 않는다.

다음 폴더를 만들고 `discover_data`와 `AnomalyMetrics`를 실행했다.

```text
train/good/a.png
val/good/a.png
test/good/b.png
test/defect/c.png
```

결과: `split=val`, `labels=[0]`, `evaluable=False`, `threshold=None`. 정상·불량이 모두 있는 test는 사용되지 않는다. GUI는 anomaly의 val 탭을 비활성화하므로 외부에서 가져온 val 데이터가 평가에 사용되는 사실도 파악하기 어렵다.

또한 정상 폴더를 직접 root로 지정하면 인접 평가 폴더를 탐색하지 않는다. 평평한 학습 폴더 안의 이미지는 전부 정상으로 간주하므로 불량이 섞이면 정상 메모리에 포함될 수 있다.

### 3. 점수 계산이 대표 참조 구현과 다름 — 품질 영향 검증 필요

`python/patchcore.py:425`: 각 패치의 점수에 기본 9개 이웃까지의 평균 거리를 사용한다. Anomalib의 `num_neighbors=9`는 이와 다르다. 패치 점수는 최근접 1개로 계산하고, 추가 이웃은 이미지 점수 재가중에 사용한다.

현재 평균 방식에서는 드물게 등장하는 정상 특징도 점수가 커질 수 있다. 실제 함수에 단일 차원 메모리 `[0,100,101,102,103,104,105,106,107]`과 질의 `[0,90]`을 넣어 확인했다.

| 질의 | 최근접 거리 | 현재 9개 평균 거리 |
|---|---:|---:|
| 0 — 저장된 특징과 동일 | 0 | 92 |
| 90 — 저장된 특징과 다름 | 10 | 22 |

이는 점수 순위가 뒤집힐 수 있다는 구성 예시이며, 사용자의 실제 특징 분포에서 발생했다는 증거는 아니다.

`python/patchcore.py:411`: 이미지 점수도 원시 패치 점수의 최대값이 아니라 확대·Gaussian smoothing을 마친 지도의 최대값이다. 28×28 패치 지도에 단일 1.0 피크를 만든 뒤 현재 224×224 처리 경로에 넣으면 최대값이 0.368466으로 감소했다. Amazon 참조 구현은 이미지 점수를 지도 smoothing 전에 계산한다. 따라서 작은 국소 이상이 주변 점수와 섞이는 영향이 이미지 판정에도 반영된다. 감소 자체만으로 오검출을 증명하지는 않는다.

### 4. 히트맵 색상으로 이미지 간 심각도를 비교할 수 없음 — 재현됨

`gui/core/inference_engine.py:272` → `gui/core/heatmap.py:23`: 각 이미지의 최소/최대로 색상을 다시 정규화한다.

`[[1,2],[3,4]]`와 그 10배 점수 지도가 완전히 같은 표시 지도로 변환되는 것을 확인했다. 정상 이미지에도 상대적으로 높은 위치가 붉게 보일 수 있다. 이 표시 정규화는 숫자 판정 점수를 바꾸지는 않는다.

### 5. 입력 해상도와 평가 방식의 한계

기본 전체 이미지를 224×224로 축소한다. 예를 들어 2048픽셀 폭 이미지의 10픽셀 결함은 약 1.1픽셀로 작아진다. 현재 사용자의 원본 해상도/결함 크기는 확인하지 않았다. ROI 크롭 또는 더 큰 입력 크기의 효과를 실제 데이터에서 비교해야 한다.

현재 선택된 평가 split에서 F1 최적 임계값을 정하고 같은 데이터로 F1을 보고한다. test를 보정에 사용했다면 그 수치를 독립 시험 성능으로 간주할 수 없다. 보정과 최종 성능 검증을 분리해야 한다.

## 실행한 검증

환경: macOS, Python 3.11.15, CPU. Windows/RTX 사용 환경의 성능 측정은 아니다.

```sh
QT_QPA_PLATFORM=offscreen PYTHONPATH=gui:python python -m pytest -q \
  tests/test_patchcore_runtime.py tests/test_patchcore_data.py \
  tests/test_patchcore_scores.py tests/test_patchcore_model_inspection.py
```

결과: **30 passed**, 11.93초. Qt API deprecation 경고 8건. 동작/일관성 검증이며 산업 데이터 정확도 시험은 아니다.

추가로 공식 ImageNet V1 ResNet18 가중치, 224 입력, 기본 대표 비율 1%, 이웃 9개로 작은 합성 실험을 실행했다. 정상 12장은 사인/코사인 무늬에 독립 잡음을 추가하여 생성했다. 평가는 별도 생성한 정상 4장, 붉은 2×2 결함 4장, 24×24 결함 4장이다. 난수 시드 810, CPU 스레드 2개다.

이는 현재 경로가 빠르게 특징을 구축하면서 쉬운 합성 불량을 구분할 수 있다는 확인이다. **기본 Wide-ResNet50-2, 저대비 실제 불량, 사용자 데이터의 검출 성능을 검증한 결과가 아니다.**

기존 `tools/patchcore_pretrained_smoke.py`도 가중치 로드, 유한한 출력, 저장·복원 일치 여부를 검사한다. 실제 정상/불량 검출 성능을 보장하는 테스트는 아니다.

## 개선 우선순위

1. 완료 상태를 ‘특징 구축 완료 / 임계값 미보정 / 판정 준비 완료’로 분리한다. 정상·불량 수, 선택된 평가 split, 실제 정상 학습 수, 메모리 크기를 완료 화면에 표시한다.
2. 보정 split을 명시적으로 선택하고 두 클래스 존재 여부를 사전에 검증한다. 자동으로 test를 소모하는 방식 대신 보정 데이터와 독립 시험 데이터를 구분한다. 정상 데이터만 있는 경우에는 별도 정상 검증셋의 목표 오검출률에 따른 임계값 보정 모드를 제공하고, 이 모드로 불량 검출률까지 검증했다고 표시하지 않는다.
3. 표준에 맞춘 점수 모드를 구현·비교한다. 최근접 패치 점수와 smoothing 전 이미지 점수를 분리하고 재가중 지원을 검토한다. 기존 모델의 점수/임계값 의미가 바뀌지 않도록 체크포인트에 모드 버전을 저장해야 한다. 새 방식은 새 임계값 보정이 필요하며 ONNX와 Python의 점수 일치도 함께 검사해야 한다.
4. 이미지별 상대 히트맵과 모델 공통 스케일 히트맵을 구분하고 범례를 표시한다. 이미지 임계값을 근거 없이 픽셀 판정 임계값으로 재사용하지 않는다.
5. 사용자 PC 내부에서 정상·불량 점수 분포, 누락 검출/오검출 수, 결함 크기별 결과를 평가한다. 이미지나 가중치를 외부로 보낼 필요는 없다. 해상도/ROI, 대표 패치 비율, 이웃 계산 방식을 비교한 뒤 결정한다.

초기 분석 시점에는 런타임 변경을 수행하지 않았다. 이후 3.65에서 아래 수정이 반영됐다.

- 미보정 모델의 ONNX 내보내기를 차단하고, 크롭·입력 범위 계약을 JSON에 저장했다.
- C++ 파일 추론이 uint16 전체 범위 입력을 처리하도록 보완했다.
- 정상·불량을 모두 가진 split을 보정 대상으로 우선 선택하고, 미보정 완료 상태를 UI에 분리해 표시했다.
- 새 모델은 표준 최근접 패치 점수 및 이미지 재가중을 사용하며, 이전 체크포인트는 이전 점수 정의를 유지한다.
- SAM2 변형 변경의 Qt 슬롯 예외를 수정했다.

## 후속 소스 검토: 완료 여부 및 ONNX 배포 결함

사용자의 후속 요청에 따라 동일 커밋 `5df833b`를 다시 검토했다. 앞선 보고서 외 실행 코드 변경은 없었다. 검토 범위는 PatchCore 학습·추론·ONNX·C++ 판정 경로와 최근 SAM2 가중치 적용 변경이다. 모든 태스크·모델·Windows 설치본의 전체 검증을 수행한 것은 아니다.

**판정: 수정 필요. 완료 상태 아님.**

1. **[P1] 미보정 임계값을 0으로 변환하여 배포함.** `python/export_patchcore_onnx.py:90`에서 `None`을 `0.0`으로 바꾼다. `cpp/src/vision_inference.cpp:1084`는 점수가 임계값 이상이면 불량으로 판정한다. PatchCore 거리는 0 이상이므로 미보정 모델을 이 경로로 배포하면 모든 유효 점수가 불량 판정 대상이다. GUI의 ‘미보정’ 상태와 의미가 달라진다. 실제 작은 ONNX 그래프를 생성·검증해 `source_threshold=null`, `exported_threshold=0.0`, `verification=passed`를 확인했다. C++ 판정 부분은 소스로 확인했으며 이 재현에서 C++ 실행 파일을 새로 빌드한 것은 아니다. 해결: 미보정 배포를 명시적으로 거부하거나 SDK까지 미보정 상태를 지원해야 한다.

2. **[P1] 학습/추론 전처리가 배포 계약에 보존되지 않음.** `python/export_patchcore_onnx.py:118`의 전처리 설정에는 모델의 `center_crop`이 없다. 크롭이 설정된 테스트 객체를 내보냈을 때 해당 필드가 누락되면서도 검증에 통과했다. Python은 `python/patchcore_data.py:95`에서 크롭을 적용하고 C++는 전달받은 설정에 크롭이 있을 때만 이를 적용하므로 입력 영역이 달라진다. 또한 Python은 PIL bilinear와 16비트 전체 범위 처리를 사용하지만 export는 OpenCV bilinear/antialias=False/255 스케일을 고정 선언한다. 해결: 실제 사용한 전처리를 보존하고 동일 원본 이미지로 Python 및 배포 경로를 비교해야 한다.

3. **[P1] SAM2 변형 선택 시 Qt 슬롯 예외.** `gui/widgets/model_manager_widget.py:100`이 `currentIndexChanged(int)`를 경로 인자를 받는 `_update_sam2_apply_state`에 연결한다. index 1 이상에서 `Path(int)`가 실행된다(`:149`). 실제 `ModelManagerWidget`에서 Tiny→Small로 변경하여 `TypeError: expected str, bytes or os.PathLike object, not int`를 확인했다. 예외로 버튼 상태 갱신이 중단되며 앱 전체 종료를 재현한 것은 아니다. 해결: 인덱스 신호와 다운로드 경로 콜백을 분리한다.

4. **[P2] Python에서 동작하는 작은 메모리 뱅크를 ONNX가 거부함.** Python 추론은 `k=min(n_neighbors, bank_size)`를 사용하지만 ONNX wrapper는 `n_neighbors > bank_size`이면 실패한다(`python/export_patchcore_onnx.py:37`). 뱅크 4행/이웃 9개로 해당 오류를 재현했다. 224 입력 정상 이미지 1장, 대표 비율 1%인 경우에도 대표 패치는 7개여서 기본 이웃 9개와 충돌한다. 해결: 두 실행 경로의 유효 k 계산을 일치시킨다.

5. **[P2] 앞서 확인한 보정/평가/표시 문제는 그대로 남아 있음.** 정상만 있는 val이 test 평가를 가리는 문제, 미보정 학습 완료 표시, 이미지별 상대 히트맵, 점수 방식 차이가 수정되지 않았다. 점수 방식의 품질 영향은 실제 데이터 평가가 더 필요하며 무조건 오류라고 단정하지 않는다.

### 기존 검사에서 놓친 이유

`tests/test_patchcore_onnx_export.py`는 작은 합성 백본, 유효한 숫자 임계값, 크롭 없음, 충분한 뱅크를 대상으로 한 단일 성공 사례다. exporter 검증도 이미 전처리된 무작위 텐서의 그래프 출력만 비교한다. 따라서 원본 이미지 전처리, 미보정 의미, SDK 판정까지 일치하는지 확인하지 못한다.

`tests/test_model_manager_ui.py`는 기본 Tiny에서 적용을 검사하지만 Small/Base+/Large로 실제 콤보박스를 변경하는 신호 경로를 검사하지 않는다.

위 기존 30개 검사에 `test_patchcore_onnx_export.py`, `test_model_manager_ui.py`를 추가하여 **34 passed, 11 warnings, 12.25초**를 확인했다. 별도 경계조건 재현에서 위 결함을 발견했다. ‘테스트 통과’만으로 기능 전체 완료를 선언할 수 없다.

후속 검토에서 확인한 P1/P2 항목은 3.65 구현과 회귀 테스트로 반영했다. C++은 이 개발 환경에
CMake가 없어 실제 바이너리 빌드를 실행하지 못했다.
