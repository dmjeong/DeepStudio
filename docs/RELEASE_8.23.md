# 8.23 — 스레드 수를 지정하지 않는 BW8 병렬 추론

eVision/BW8 예제는 기존 `model.InferEvision(roi)` / `InferBW8(...)` 호출에서
독립된 작업 공간을 자동으로 빌린다. 호출자가 스레드 개수를 알거나 Context 배열을
선언할 필요가 없다. 사용 중인 공간은 다른 호출에 배정하지 않고, 모두 사용 중일 때만
공간을 추가한다. 호출 종료와 예외 발생 시 공간을 반환하고 다음 호출에서 재사용한다.

작업 공간은 전처리 캐시·입력·출력 메모리다. 스레드를 생성하거나 점유하지 않는다.
스레드 수가 다른 OMP 구간들과 기존 작업 스레드가 같은 모델을 호출할 수 있다.
모델과 ONNX Runtime CPU 세션은 하나만 유지하고, 모델 재로드·복호화는 하지 않는다.
확보한 작업 공간은 모델이 해제될 때까지 유지한다. 스레드 종료와 모델 해제 순서,
추론 중 원본 이미지·ROI 위치를 변경하지 않는 조건은 그대로 필요하다.

## 적용

기존 솔루션은 `example/cpp/with_evision/classifier.h`를 교체하고 다시 빌드한다.
직접 만들었던 Context 배열과 스레드 번호 전달은 제거할 수 있다.

```cpp
auto result = model.InferEvision(roi);
```

기존 명시적 `CreateContext()`와 Context 전달 API도 유지한다. 공간을 미리 만들어
준비 추론할 때 사용할 수 있다. 명시적 Context 하나를 여러 호출이 공유하면 그 공간의
잠금으로 순차 처리하며, 자동 호출은 비어 있는 공간을 각각 대여한다.

재학습·ONNX 재내보내기·키 변경·ORT SDK 교체는 필요 없다. ONNX 그래프, 입력 전처리,
정밀도와 검증된 실행 설정을 바꾸지 않는다. 생성자의 준비 추론은 유지하지만 처음으로
추가 동시 작업 공간이 필요할 때는 메모리 할당과 전처리 캐시 준비 비용이 발생할 수 있다.
`inference_ms`에는 풀 대여·새 공간 할당 시간이 포함되지 않으므로 전체 호출 시간은
호출부의 시계로 측정한다.

병렬 빌드 검증에서 예제들이 같은 assets/DLL 경로로 동시에 복사하다 실패하는 문제도
재현했다. `copy_assets.cmake`의 파일 잠금으로 복사 작업을 직렬화해 수정했다.

## 검증

로컬 Apple M4 / macOS / C++17 / ORT 1.29.0에서 확인했다.

- BW8 Release 및 OpenMP Debug/Release CTest 각 5개 통과.
- 기존 자동 호출, 명시적 작업자별 Context, 공유 Context, 3→11→2→17개로 바뀌는
  호출자 수를 평문·암호화 모델로 비교했다. OMP를 켠 검사는 독립 팀 두 개(3·5개
  작업자)의 동시 호출도 포함해 총 15,552회 클래스·confidence·확률이 순차 실행과
  같았다. 잘못된 입력 후 재호출과 다른 모델의 Context 거부도 검사했다.
- EfficientNet B0 구조의 기존 로컬 테스트 가중치에서 호출자 수 1·3·7개를
  평문·암호화 모델로 실행한 총 880회가 순차 실행과 바이트 단위로 일치했다.
  사용자 데이터의 정확도 평가를 의미하지 않는다.
- B0 단일 호출의 8.22/8.23 ABBA 비교(구간별 150회)는 이전 p50 4.97~4.99ms,
  자동 공간 p50 약 4.94ms였다. 이 PC의 측정이며 모든 PC의 성능을 보장하지 않는다.

Windows VS2017 및 실제 eVision SDK 장비는 로컬에서 검증하지 못했다.
기존 Windows CI의 v141 Debug/Release 검사에 변경 예제와 회귀 검사가 포함된다.
