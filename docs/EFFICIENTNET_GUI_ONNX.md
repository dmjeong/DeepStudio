# Studio 추론 버튼의 EfficientNet CPU 경로

2026-09-18 수정. 사용자가 말한 20 ms는 Studio에서 추론 버튼을 누른 뒤
배치 표에 표시되는 이미지별 `추론 시간 (ms)`였다. 이전 ONNX 최적화는
독립 Python/C++ 실행 경로에만 적용됐고, 이 버튼은 여전히 PyTorch를 호출했다.
따라서 이전 C++ 수치를 이 화면의 성능으로 해석하면 안 된다.

## 적용 방법과 화면

`deepstudio3`를 업데이트하고 Studio를 다시 실행한다. 기존 EXE 사용자는 새 소스로
Windows에서 다시 빌드해야 한다. 기존 EXE의 동작은 git pull만으로 바뀌지 않는다.
별도 모델 변환 명령 없이 EfficientNet 체크포인트를 로드하고 CPU에서 추론한다.

- CPU EfficientNet의 판정은 검증을 통과한 ONNX Runtime으로 실행한다. 준비 실패 시
  기존 PyTorch 모델로 계속 실행한다. GPU 및 다른 모델 경로는 유지한다.
- 배치 표 위의 **선택 이미지** 영역에 `ONNX Runtime cpu (4 threads)`와
  파일 읽기·전처리·모델·후처리 시간이 표시된다. 표의 시간 셀 툴팁에도 저장한다.
- 표의 기존 시간은 파일 읽기/디코딩 + crop/resize/정규화 + 모델 + 수치 후처리다.
  모델 시간만으로 바꾸거나 파일 읽기 시간을 빼서 숫자를 줄이지 않는다.
- Grad-CAM 체크 상태를 유지한다. 판정은 화면에 표시된 엔진, 추가 Grad-CAM은 같은 가중치의
  PyTorch로 계산하며 별도 시간을 표시한다. Grad-CAM을 켠 전체 작업은 더 오래 걸린다.
- 이미지 선택/작업 기록 복원은 저장된 판정과 시간만 표시한다. 재추론하지 않는다.

## 준비와 호환성

CPU 모델을 로드한 뒤 작업 워커에서 batch=1의 고정 입력 ONNX(opset 17)를 만든다.
이미 로드한 가중치를 사용하고 원본 체크포인트는 수정하지 않는다. 새 가중치 다운로드도 없다.
기존 전처리, 채널 수, crop과 클래스 순서를 보존한다. FP32를 유지한다.

ORT는 CPUExecutionProvider, ORT_ENABLE_ALL, sequential, 4 intra-op threads를 기본으로 사용한다.
로드한 PyTorch 모델과 seeded/zero 입력의 logits를 비교하고 10회 워밍업한다.
변환·검증·워밍업은 이미지별 측정 전에 수행되며 시작 대기에 포함된다.
ALL에서 출력 검증이 실패할 때만 BASIC, DISABLED를 차례로 다시 검증한다.
동일한 허용 오차를 통과한 ONNX 세션만 사용하고 선택한 수준을 결과에 기록한다.
화면의 `[기본 최적화]` 또는 `[최적화 꺼짐]`은 이러한 재검증 경로를 뜻한다.
현재 분류 FP32 parity 프로필은 `atol=0.001`, `rtol=0.0005`이며 적용 값은 결과 JSON의
`runtime_verification_tolerance`와 export manifest의 `export.verification_tolerance`에 남는다.
오차가 `0.00052`이고 이전 실행파일에서 계속 실패하면, 소스만 내려받는 것으로는 실행파일이
바뀌지 않으므로 이 커밋 이후의 Windows EXE를 다시 빌드해야 한다.
자동 모드에서 모든 수준의 검증, 변환 또는 라이브러리 준비가 실패하면 해당 ONNX를
사용하지 않고 기존 PyTorch로 배치를 계속한다. 화면에는 `PyTorch cpu`와
`[ONNX 준비 실패 → PyTorch]`를 표시하고 선택 이미지/시간 셀의 툴팁과 로컬 작업 로그에
원래 오류를 보존한다. 결과 캐시에도 `runtime_warning`을 저장한다. 한 작업에서
ONNX 준비는 한 번만 시도한다. `runtime=onnx`와 명시적 내보내기는 실패를 반환한다.
낮은 최적화 수준에서는 추론 속도가 느려질 수 있으므로 해당 PC에서 표시 시간을 확인한다.

일반 데스크톱 버튼은 독립 작업 프로세스를 매번 시작하므로 작업 시작마다 준비가 있다.
한 배치의 모든 이미지는 같은 세션을 사용한다. in-process GUI 경로는 같은 모델의
세션을 다음 버튼 클릭에도 재사용하고 모델 교체 시 제거한다.
기존 GUI 의존성인 onnx/onnxruntime을 사용한다. 새 실행 라이브러리는 추가하지 않았다.

## 로컬 실측: Apple M4, Windows/i7 아님

B0, FP32, 모델 입력 1×1×224×224, 2클래스, 고정 시드 임의 가중치.
고정 시드 RGB PNG를 파일에서 읽고 기존 규칙으로 gray 변환했다.
Grad-CAM 꺼짐, 4 threads, 조건별 별도 프로세스, 순차 측정, warmup 10 + 300회.
반복 측정의 파일 캐시는 따뜻한 상태다. 실제 학습 데이터 정확도 검증은 아니다.

| 실제 런타임 | 원본 크기 | 추론 p50 | 추론 p95 | 추론 최대 | 8 ms 이내 |
|---|---|---:|---:|---:|---:|
| PyTorch | 224×224 | 90.767 ms | 92.826 ms | 175.673 ms | 0/300 |
| ONNX Runtime | 224×224 | 6.037 ms | 6.261 ms | 8.596 ms | 299/300 |
| ONNX Runtime | 2048×2048 | 33.599 ms | 34.380 ms | 37.861 ms | 0/300 |

**모델 입력이 224여도 원본 파일이 2048이면 디코딩 등의 비용은 더 크다.**
같은 엔진으로 측정한 위 시간은 실제 `inference_sec`이며 UI/미리보기 저장은 제외한다.
실제 Qt 버튼도 독립 프로세스를 실행해 ONNX 경로와 화면 표시를 확인했다.
별도 gray PNG의 첫 버튼 실행에서는 추론 11.527 ms(파일 읽기 4.476 ms)가 관측됐다.
따라서 반복 p95를 첫 이미지나 모든 요청의 8 ms 보장으로 바꾸지 않는다.
[환경·가중치 해시·원시 시간·첫 버튼 표본](benchmarks/efficientnet-gui-m4-20260918.json)

사용자 i7의 기존 20 ms와 위 M4의 PyTorch 90 ms는 서로 다른 장비의 결과다.
**Windows/i7에서 8 ms 달성 여부와 Windows EXE 빌드는 아직 검증하지 못했다.**
업데이트 후 같은 모델/이미지를 추론하면 새 표시에서 실제 런타임과 병목을 확인할 수 있다.

개발용으로 버튼과 같은 엔진을 별도로 반복 측정하려면 Studio Python 환경에서:

```bat
python tools\cpu_benchmark.py --weights my_model.pt --images test_images --runtime auto --threads 4 --warmup 10 --runs 300 --output gui-cpu-results
```

`--runtime pytorch`는 이전 경로 비교용이다. `--gradcam`을 추가하면 CAM도 별도로 측정한다.
`benchmark.json`의 actual_runtime, runtime_warning과 onnx_intra_op_threads로
적용된 설정을 확인한다. 자동 모드가 PyTorch로 전환된 측정은 ONNX 성능이 아니다.

## 회귀 검증

실제 B0의 gray/RGB·crop·직사각 입력에서 PyTorch/ONNX 결과를 비교했다.
ONNX 준비 후 PyTorch forward를 강제로 실패시켜도 판정은 성공하고,
Grad-CAM을 켰을 때는 PyTorch forward와 역전파가 실행되는 것을 확인했다.
실제 Qt 버튼의 두 실행 경로, 세션 재사용, 표시 위젯의 가시성, 결과 캐시 복원,
변환 실패 시 자동 모드 복구, 명시적 ONNX 실패, 원본 이미지/가중치 불변성도 검증했다.
대상 테스트 목록과 결과는 PDCA 분석 문서에 기록한다.

## 최대 오차 2.8339844 보고에 대한 후속 조치

사용자의 학습 가중치/양쪽 출력값이 없어 이 오류의 원인은 아직 확정하지 못했다.
최대 절대 오차만으로 미세 반올림이라고 판단하거나 허용 오차를 늘리지 않았다.
출력 형상 및 NaN/무한대 검사는 그대로 유지한다. 분류 logits에는 `atol=1e-3,
rtol=5e-4`의 FP32 parity profile을 적용한다. 이는 CPU ONNX kernel의 연산 재배치로
생기는 작은 상대 오차만 허용하며, near-zero 출력의 absolute floor와 큰 오차 검사는 유지한다.

이제 실패 메시지는 최적화 수준과 입력(seed/zero), 실패 원소의 PyTorch/ONNX 값,
허용 오차 배수, 출력 범위, PyTorch/ORT 버전을 포함한다. 다른 최적화 수준에서
검증을 통과하면 그 ONNX 설정으로 실행하고, 계속 실패하면 자세한 메시지를 남긴다.
검증 재시도는 최적화에서 생긴 불일치에 대응할 수 있지만 모든 변환 오류의 해결을 보장하지 않는다.
공통 내보내기 검증에도 자세한 오류를 제공하며, GUI의 자동 재시도 선택을 C++ 배포 설정에
자동 적용하지는 않는다. C++ 배포는 그 환경에서 별도로 수치/속도를 검증해야 한다.

공식 학습 B0의 RGB/gray 적응 모델을 Mac에서 확인한 최대 절대 오차는 약 1.50e-5였고,
이 환경에서는 사용자 오류가 재현되지 않았다. 가중치는 테스트용 작업 폴더에서만 사용했고
저장소에 포함하지 않았다. [추가 검증 수치](benchmarks/efficientnet-onnx-validation-m4-20260918.json).
재시도 성공/전체 실패 경로는 실제 ORT 출력에 오차를 주입해 검증했다. 이것은 사용자의
실제 실패 가중치를 재현한 테스트와 구분한다.

## ONNX 검증 실패 때문에 기존 추론까지 막힌 문제 수정

앞선 변경은 ONNX 준비를 필수 조건으로 만들어 모든 검증이 실패하면 배치 전체를
중단시켰다. 자동 모드는 이제 기존 PyTorch로 실행을 계속한다. ONNX 수치 검증을
완화하지 않으며 PyTorch 자체 오류와 비정상 출력은 계속 실패로 보고한다.

사용자의 보안 가중치/이미지 업로드는 필요하지 않다. 자체 생성한 B0 가중치로
변환 실패와 ALL/BASIC/DISABLED 출력 불일치를 주입해 기존 추론이 유지되는지 검증한다.
이 수정은 추론 기능의 복구이며, 사용자 모델의 ONNX 수치 불일치 원인이나
Windows/i7의 8 ms 목표를 해결했다는 의미는 아니다.
